# Tete-a-tete

Tete-a-tete — голосовые комнаты до 5 человек для геймеров на Windows 11. Голос идёт только напрямую между участниками (P2P mesh на WebRTC). Сервер лишь знакомит участников и никогда не передаёт голос.

Подробный дизайн и обоснования: [Tete-a-tete: как работает сервис](https://claude.ai/artifact/V3rggxW3TNBDWA4mU5LQar). Этот файл — выжимка. При расхождении сверяйтесь с документом и обновляйте оба.

Имена: приложение — `Tete-a-tete`; протокол ссылок — `tete-a-tete://r/<id>`; пакеты, образы и репозиторий — `tete-a-tete`. Домен пока не выбран, в примерах стоит `app.example.com`.

## Ключевые решения (не менять без обсуждения)

- **Только P2P.** Голос никогда не идёт через сервер: нет TURN, SFU, MCU. Если пара не соединилась напрямую, голос пересылает третий участник комнаты.
- **Mesh, до 5 участников, только голос** (Opus). Видео и текстового чата нет.
- **Клиент — только приложение Electron + Angular для Windows 11.** Браузерного клиента нет. Пользователи сидят за домашним роутером; мобильные сети и другие ОС не поддерживаются.
- **Бэкенд — Python и FastAPI**, один процесс uvicorn.
- **Доступ по ссылке** со случайным id комнаты: не короче 10 символов, из криптостойкого генератора. Нет аккаунтов, владельца комнаты, `kick` и `lock`.
- **Сервер хранит всё в памяти.** На диск попадает только обезличенная статистика соединений: раз в сутки в `stats/YYYY-MM.jsonl` на отдельном томе, независимо от логов. Служебные логи ротируются и не содержат IP из нашего кода.
- **Свой STUN** в том же процессе Python, что и сигналинг, на `3478/udp` и `3479/udp`. Второй порт нужен для определения типа NAT. Сторонние STUN не используем.
- **Сигналинг только по `wss://`:** в offer и answer передаются отпечатки DTLS, их нельзя отдавать без шифрования.

## Архитектура

| Компонент | Где | Что делает |
| --- | --- | --- |
| Caddy | VPS, `80/tcp`, `443/tcp` | HTTPS и Let's Encrypt, проксирует `/ws`, раздаёт `site/` |
| Сигналинг (FastAPI) | VPS, `127.0.0.1:8080` | Комнаты в памяти, пересылка `signal`, выбор ретранслятора, статистика |
| STUN | тот же процесс, `3478/udp`, `3479/udp` | Отвечает клиенту его внешним IP и портом |
| Клиент | ПК пользователя | Electron: WebRTC в Chromium, UPnP, правило брандмауэра, проверка сети, push-to-talk |

Деплой — Docker Compose, оба контейнера в `network_mode: host`: STUN и Caddy должны видеть настоящие IP клиентов. В Caddyfile `/ws` обрабатывается в отдельном `handle` до `try_files`, иначе WebSocket-запрос перепишется в `/index.html`. Журнал запросов Caddy не включается, служебные логи Docker ротируются (3 файла по 10 МБ). Статистика лежит на отдельном томе `stats`, и ротация логов её не трогает.

Сигналинг запускается так:

```
uvicorn app.main:app --host 127.0.0.1 --port 8080 --workers 1
  --ws-ping-interval 15 --ws-ping-timeout 15 --ws-max-size 65536
  --proxy-headers --forwarded-allow-ips 127.0.0.1 --no-access-log
```

Строго один воркер: комнаты живут в памяти процесса. `--no-access-log` обязателен: журнал запросов uvicorn содержит IP клиентов.

## Структура репозитория (план)

```
server/     сигналинг + STUN: Python, FastAPI; проект uv (pyproject.toml)
protocol/   schema.json — JSON Schema протокола, генерируется из Pydantic-моделей сервера
client/     приложение Electron (TypeScript)
  src/main/         главный процесс: окно, трей, PTT, UPnP, брандмауэр, сон и выход, обновления
  src/preload/      мост через contextBridge
  renderer/         проект Angular CLI
    src/app/core/   звонок: сигналинг, WebRTC, ретрансляция, статистика — без Angular
    src/app/...     компоненты; CallService отдаёт состояние core через signals
site/       страница /r/<id>, загрузка установщика, файлы обновлений
deploy/     docker-compose.yml, Caddyfile
```

Стек:
- **Сервер:** Python 3.13, FastAPI, uvicorn[standard], Pydantic v2, asyncio (STUN на `DatagramProtocol`), `maxminddb`. Инструменты: uv, ruff, mypy (strict), pytest, pytest-asyncio.
- **Клиент:** TypeScript (strict), Electron, Angular (standalone-компоненты, signals, без zone.js), Angular CLI для страницы, esbuild для main и preload, electron-builder (NSIS), electron-updater, zod, vitest.
- **Сайт:** статическая страница `/r/<id>` и страница загрузки на TypeScript. Клиент и сайт — npm workspaces.

## Протокол сигналинга

JSON по одному WebSocket `wss://<домен>/ws`, в каждом сообщении есть поле `type`.

**Источник истины — Pydantic-модели в `server/app/protocol.py`.** Из них генерируется `protocol/schema.json`, а из него — TypeScript-типы и zod-схемы клиента в `client/src/protocol.gen.ts`. Сгенерированные файлы руками не правят: меняется модель, затем запускается `gen:protocol`.

- **Клиент → сервер:** `create {name, net}`, `join {roomId, name, net, resumeToken?}`, `signal {to, data}`, `mute {muted}`, `pair-report {peer, result, route, family, sameIp, ms, restarts}`, `ping`, `leave`.
- **Сервер → клиент:** `joined {roomId, selfId, resumed, resumeToken, peers}`, `peer-joined {id, name}`, `peer-left {id}`, `signal {from, data}`, `mute {id, muted}`, `relay {a, b, via}`, `pong`, `error {code: room-full | bad-request}`.
- `data` в `signal` — это `{description}`, `{candidate}` или `{relayTrack: {mid, from}}`. Сервер его не читает и пересылает только внутри комнаты отправителя.
- `join` на несуществующий id создаёт комнату. Пустая комната удаляется сразу, ссылка продолжает работать.
- `resumeToken` = HMAC(`RESUME_SECRET`, roomId, peerId). В памяти он не хранится, поэтому переживает перезапуск сервера.
- `net` — итог проверки сети клиента: `{nat, upnp, cgnat, doubleNat, vpn}`.

## Константы

| Что | Значение |
| --- | --- |
| Участников в комнате | 5 |
| Длина id комнаты | ≥ 10 символов |
| WebSocket-ping сервера | раз в 15 с, ожидание ответа 15 с (флаги uvicorn) |
| Максимальный размер сообщения | 64 КБ (`--ws-max-size`) |
| `ping` клиента / таймаут `pong` | 10 с / 5 с |
| Ожидание после обрыва | 15 с, затем `peer-left` |
| Очередь `signal` на время ожидания | ≤ 50 сообщений |
| Уборка комнат | раз в 1 с |
| `restartIce()` | через 3 с в `disconnected`; при `failed` — одна попытка |
| Пар на одного ретранслятора | ≤ 2 |
| UDP-порты WebRTC в клиенте | диапазон из 16 |
| Запись статистики | раз в сутки (00:00 UTC) и при остановке сервера, файл на месяц |
| Интервалы `ms` / `restarts` в статистике | `<1s`, `1-3s`, `3-10s`, `>10s` / `0`, `1`, `2+` |
| Порог приватности статистики | в сочетаниях с `count` < 5 `asn` = `null` |
| Ротация служебных логов | 3 файла по 10 МБ |

## Правила кода

Сервер:
- Не логировать и не хранить IP, SDP и ICE-кандидаты — даже в сообщениях об ошибках. IP используется только в момент подключения: для лимитов и определения ASN. Берётся из `websocket.client.host` (uvicorn с `--proxy-headers`).
- Каждое входящее сообщение разбирается Pydantic-моделью — discriminated union по `type`. Ошибка — `bad-request`.
- В Python — snake_case, в JSON протокола — camelCase: модели с `alias_generator=to_camel` и `populate_by_name=True`.
- Всё асинхронное, никаких блокирующих вызовов в обработчиках. STUN и фоновые задачи (уборка, запись статистики) запускаются и останавливаются в lifespan приложения.
- Время берётся из подменяемых часов, чтобы таймауты тестировались без ожидания.
- Статистика пишется в `STATS_DIR`, а не в лог. Стороны пары в сочетании записываются в фиксированном порядке, чтобы A–B и B–A совпадали. При остановке (SIGTERM → lifespan shutdown) счётчики дописываются перед выходом.

Клиент:
- Главный процесс отвечает за систему: окно, трей, PTT, UPnP, брандмауэр, сон и выход. WebRTC и WebSocket сигналинга живут только на странице: `RTCPeerConnection` в главном процессе нет. Связь — IPC через узкий API preload.
- Звонок живёт в `renderer/src/app/core/` на чистом TypeScript, без импортов Angular, и тестируется в vitest. Angular только показывает состояние: `CallService` оборачивает core и отдаёт signals.
- Angular без zone.js (`provideZonelessChangeDetection`), состояние — signals. События WebRTC и опрос индикатора говорящего не должны запускать проверку изменений во всём приложении.
- Собранное приложение загружается через свой протокол `app://` (`protocol.handle`), который на любой путь отдаёт `index.html`, а не через `file://`. В разработке страница грузится с `ng serve` на `localhost:4200`.
- Безопасность окна: `contextIsolation` и `sandbox` включены, `nodeIntegration` выключен. CSP: скрипты только `'self'`, стили `'self' 'unsafe-inline'` — Angular вставляет стили компонентов в страницу.
- Микрофон запрашивается до создания `RTCPeerConnection`.
- Offer отправляет новичок — тот, кто получил `joined`. Коллизии решает perfect negotiation, роль polite определяется сравнением id.
- ICE-кандидаты буферизуются до `setRemoteDescription`.
- Обрыв WebSocket не трогает P2P-соединения. `restartIce()` ждёт возвращения сигналинга. После каждого `joined` клиент сверяет `peers` со своими соединениями.
- Mute = `track.enabled = false` + сообщение `mute`, без пересогласования.
- Индикатор говорящего — через `getSynchronizationSources().audioLevel`, не через WebAudio.
- `setWebRTCIPHandlingPolicy('default_public_and_private_interfaces')` и `setWebRTCUDPPortRange` вызываются до первого соединения.

## Оркестрация

Процесс берётся из [superpowers](https://github.com/obra/superpowers), знания по языкам и проверки безопасности — из плагинов [wshobson/agents](https://github.com/wshobson/agents), правила проекта — из агентов и скиллов в `.claude/`.

Работа начинается со скилла `/stage N` (весь этап) или `/stage N.M` (один пункт): спецификация (`brainstorming`) → ветка → план (`writing-plans`) → исполнение субагентами с ревью каждой задачи (`subagent-driven-development`) → проверка поведения (`qa-engineer`) → финальное ревью → `/verify` → `[x]` в плане → завершение ветки. Спецификации и планы лежат в `docs/superpowers/`.

**Маршрутизация.** Шаблоны superpowers запускают исполнителя как `general-purpose`. В этом проекте исполнитель задачи — агент её зоны, задача на две зоны делится на две задачи.

| Зона | Агент |
| --- | --- |
| `server/`, модели протокола | `server-engineer` |
| `client/renderer/src/app/core/` | `webrtc-engineer` |
| `client/src/main/`, `client/src/preload/`, сборка и установщик | `electron-engineer` |
| Остальной `client/renderer/`, `site/` | `ui-engineer` |
| `deploy/`, `server/Dockerfile`, `.github/workflows/` | `infra-engineer` |

**Проверка поведения.** `qa-engineer` работает после всех задач плана, до финального ревью. Он пишет собственные тесты на граничные, негативные, временные и гоночные случаи и на приватность и прогоняет сценарии «Готово, когда». Рабочий код он не правит. Каждая найденная ошибка закрепляется тестом с пометкой `xfail(strict=True)` или `test.fails` и исправляется агентом зоны.

**Ревью.** `invariants-reviewer` только читает и ищет нарушения ключевых решений, приватности, протокола и констант. Он участвует в финальном ревью каждой ветки и в ревью задач, которые трогают логи, статистику, протокол, IP или безопасность окна. Для работы с поверхностью атаки до плана запускается `security-scanning:threat-modeling-expert`, а в финальное ревью добавляется `comprehensive-review:comprehensive-review-security-auditor`.

**Скиллы проекта:** `stage`, `verify`, `protocol-change`, `webrtc-call-engine` (загружается в `webrtc-engineer`).

**Плагины** перечислены в `.claude/settings.json`: superpowers и из wshobson — python-development, javascript-typescript, security-scanning, backend-api-security, frontend-mobile-security, comprehensive-review, cicd-automation. Плагины wshobson со своим процессом разработки (tdd-workflows, full-stack-orchestration, agent-teams, conductor) не подключаются: они конкурируют с superpowers. Установка из Git Bash: `bash .claude/install-plugins.sh`. В PowerShell `bash` запускает WSL, поэтому там так: `& (Join-Path (Split-Path (Split-Path (Get-Command git).Source)) 'bin\bash.exe') .claude/install-plugins.sh`. После установки перезапустите Claude Code.

**Хуки.** Ручная правка `protocol/schema.json` и `client/src/protocol.gen.ts` блокируется. Флаги `--no-verify` и `--no-gpg-sign` блокируются (правило из block-no-verify в wshobson).

## План разработки

Каждый этап заканчивается проверяемым результатом. Выполненное отмечается `[x]`.

### Этап 0. Репозиторий и общий протокол

- [ ] 0.1 Сервер: проект uv в `server/` (Python 3.13, FastAPI, uvicorn[standard], Pydantic v2), ruff, mypy strict, pytest. Клиент и сайт: npm workspaces `client` и `site`, TypeScript strict, ESLint, Prettier, vitest.
- [ ] 0.2 `server/app/protocol.py`: Pydantic-модели всех сообщений с camelCase в JSON, генератор id комнаты.
- [ ] 0.3 Генерация протокола: `protocol/schema.json` из Pydantic, из него — TypeScript-типы и zod-схемы в `client/src/protocol.gen.ts`. Скрипт `gen:protocol`.
- [ ] 0.4 CI: ruff, mypy и pytest для сервера; lint, typecheck и vitest для клиента; проверка, что сгенерированный протокол актуален (`gen:protocol`, затем `git diff --exit-code`).
- [ ] 0.5 Заказать сертификат подписи кода: выпуск занимает время, а нужен он к этапу 11.

Готово, когда: `uv run pytest` и `npm test` проходят, модели протокола покрыты тестами, CI зелёный.

### Этап 1. Сервер сигналинга

- [ ] 1.1 WebSocket-эндпоинт FastAPI `/ws`, uvicorn на `127.0.0.1:8080` с одним воркером и `--ws-max-size 65536`. Каждое сообщение — через Pydantic, ошибка — `bad-request`.
- [ ] 1.2 Комнаты в памяти: `create`; `join`, который создаёт комнату, если её нет; лимит 5 → `room-full`; `leave`; рассылка `peer-joined` и `peer-left`.
- [ ] 1.3 Пересылка `signal` только внутри комнаты, `mute`.
- [ ] 1.4 Heartbeat: WebSocket-ping средствами uvicorn (`--ws-ping-interval 15 --ws-ping-timeout 15`), ответ `pong` на `ping`.
- [ ] 1.5 Обрывы: ожидание 15 с, очередь `signal` до 50 сообщений, `resumeToken` на `hmac` + `hashlib`, `resumed: false` для освобождённых мест (множество `left`).
- [ ] 1.6 Уборка — фоновая задача asyncio из lifespan, раз в секунду: удаление участников после ожидания и пустых комнат.
- [ ] 1.7 Лимиты соединений и создания комнат на IP. IP — `websocket.client.host` при `--proxy-headers --forwarded-allow-ips 127.0.0.1`.
- [ ] 1.8 Тесты на pytest + pytest-asyncio. Модульные: логика комнат с подменяемыми часами, без сети. Интеграционные: настоящий uvicorn на случайном порту и несколько клиентов `websockets` — вход, выход, обрыв и возврат, перезапуск сервера, сценарий A/B/C из дизайна.

Готово, когда: все сценарии жизненного цикла комнаты проходят в тестах.

- [ ] 2.2 `asyncio` `DatagramProtocol` в том же процессе, запуск и остановка в lifespan. Сокеты на `3478` и `3479` для IPv4 и IPv6.
- [ ] 2.3 Ограничение частоты запросов с одного IP.
- [ ] 2.4 Тесты разбора и сборки пакетов.

### Этап 4. Клиент: первый звонок

- [ ] 4.1 Каркас: Angular CLI для страницы (standalone, zoneless, signals), esbuild для main и preload, протокол `app://` для собранного приложения, `ng serve` + Electron в разработке.

- [ ] 4.5 Воспроизведение потоков, mute, индикатор говорящего.

### Этап 5. Надёжность клиента

- [ ] 5.1 `ping` раз в 10 с. Переподключение, если `pong` не пришёл за 5 с, и сразу по событию `online`.
- [ ] 5.2 Возврат с `resumeToken`, сверка `peers` после каждого `joined`, полный перезапуск соединений при `resumed: false`.

- [ ] 5.4 `leave` по `before-quit` и `powerMonitor` `suspend`, переподключение по `resume`.

Готово, когда: обрыв WebSocket, перезапуск сервера и сон ПК не прерывают разговор остальных и восстанавливаются сами.

### Этап 6. Статистика соединений

Делается до улучшений связности, чтобы получить исходную долю неудачных пар и потом видеть эффект каждого улучшения.

- [ ] 6.1 Проба NAT при запуске: кандидаты через STUN на `3478` и `3479` → `open`, `cone`, `symmetric` или `no-udp`.
