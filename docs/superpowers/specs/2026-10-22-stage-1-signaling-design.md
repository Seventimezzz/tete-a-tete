# Этап 1. Сервер сигналинга

Дата: 2026-10-22. Пункты плана из CLAUDE.md:

> - 1.1 WebSocket-эндпоинт FastAPI `/ws`, uvicorn на `127.0.0.1:8080` с одним воркером и `--ws-max-size 65536`. Каждое сообщение — через Pydantic, ошибка — `bad-request`. Внимание: uvicorn пишет IP клиента при каждом рукопожатии WebSocket (`"WebSocket /ws" [accepted]` и отказы) в логгер `uvicorn.error` на уровне INFO, и `--no-access-log` этого не убирает. Подавить и закрепить интеграционным тестом в 1.8.
> - 1.2 Комнаты в памяти: `create`; `join`, который создаёт комнату, если её нет; лимит 5 → `room-full`; `leave`; рассылка `peer-joined` и `peer-left`.
> - 1.3 Пересылка `signal` только внутри комнаты, `mute`.
> - 1.4 Heartbeat: WebSocket-ping средствами uvicorn (`--ws-ping-interval 15 --ws-ping-timeout 15`), ответ `pong` на `ping`.
> - 1.5 Обрывы: ожидание 15 с, очередь `signal` до 50 сообщений, `resumeToken` на `hmac` + `hashlib`, `resumed: false` для освобождённых мест (множество `left`).
> - 1.6 Уборка — фоновая задача asyncio из lifespan, раз в секунду: удаление участников после ожидания и пустых комнат.
> - 1.7 Лимиты соединений и создания комнат на IP. IP — `websocket.client.host` при `--proxy-headers --forwarded-allow-ips 127.0.0.1`.
> - 1.8 Тесты на pytest + pytest-asyncio. Модульные: логика комнат с подменяемыми часами, без сети. Интеграционные: настоящий uvicorn на случайном порту и несколько клиентов `websockets` — вход, выход, обрыв и возврат, перезапуск сервера, сценарий A/B/C из дизайна.

«Готово, когда» этапа 1: все сценарии жизненного цикла комнаты проходят в тестах.

Этап 0 закрыт: модели всех сообщений, разбор с `bad-request` и генерация клиента уже есть в `server/app/protocol.py`. В `server/app/main.py` пока только пустое приложение FastAPI без документации API.

## Зачем

Сигналинг знакомит участников комнаты: ведёт список, пересылает offer, answer и кандидатов между ними и держит место за тем, у кого оборвалась связь. Голос через сервер не идёт. Этап 1 даёт серверную половину первого звонка (этап 4) и поведение при обрывах, на которое опирается этап 5.

## Цели

1. `/ws` принимает сообщения клиента, отвечает и рассылает сообщения сервера по таблице протокола.
2. Комнаты, участники, ожидание после обрыва, очередь `signal` и возврат по `resumeToken` работают так, как описано ниже, в том числе после перезапуска сервера.
3. Лимиты на IP защищают от массового открытия соединений и создания комнат.
4. В логах сервера и uvicorn нет IP, SDP, кандидатов, id комнат, имён и токенов.
5. Модульные и интеграционные тесты покрывают весь жизненный цикл комнаты.

## Решения человека (2026-10-22)

1. **Лимиты на IP:**
   - одновременных WebSocket с одного IP — не больше 20;
   - создать комнату — не чаще 10 раз за 60 с с одного IP. Считаются `create` и `join` на несуществующий id без действующего токена (решение исполнителя 4).
2. **При превышении:**
   - лишнее соединение получает отказ при рукопожатии, до `accept`;
   - лишнее создание комнаты получает новый код `error {code: rate-limited}`. Это изменение протокола по скиллу `protocol-change`.

   IP — ключ счётчика только в памяти и только пока открыто соединение или идёт окно в 60 с. В логи он не попадает.
3. **Правило клиента после `joined` с `resumed: true`.** Соединения с участниками, которых нет в `peers`, закрываются не сразу, а через 15 с, если участник за это время не пришёл через `peer-joined`. При `resumed: false` клиент, как и раньше, закрывает всё и входит новичком. `peer-joined` от участника, с которым уже есть соединение, его не трогает.

   Иначе после перезапуска сервера первый вернувшийся разорвал бы рабочие соединения с теми, кто ещё не вернулся. Реализуется в этапе 5, на этапе 1 меняется только текст правила в CLAUDE.md и дизайн-документе.

Решения по итогам финального ревью (2026-10-23):

4. **Флуд служебными кадрами** закрывается своим подклассом протокола WebSocket uvicorn (раздел «Сырой бюджет и keepalive»). Команда запуска получает `--ws app.wsproto:TeteWebSocketProtocol`, uvicorn закреплён точно.
5. **IPv6:** запись AAAA для сигналинга не публикуется, ярусы /56 и /48 откладываются до её появления (мера для 3.1 в «Разборе угроз»).
6. **Кэш IP в uvicorn** (`--proxy-headers`, до 4096 адресов в памяти процесса) — принятый риск, своё middleware не пишется.
7. **Вложенность `data`** снижена с 32 до 8 уровней: реальные данные — 2 уровня.

### Соединение

- Рукопожатие:
  - IP берётся из `websocket.client.host`. Если его нет, используется общий ключ `"unknown"`.
  - Если ключ этого IP исчерпал места, рукопожатия или глобальный предел соединений (см. «Лимиты»), сервер закрывает рукопожатие до `accept` (HTTP 403).
  - Иначе соединение принимается и учитывается до закрытия.
- Каждый текстовый кадр разбирается через `parse_client_message`.
  - Ошибка разбора и бинарный кадр — `error {code: bad-request}`. Соединение остаётся открытым.
  - Кадр больше 64 КБ закрывает сам uvicorn (`--ws-max-size`).
- `ping` в любом состоянии — `pong`.
- Соединение бывает вне комнаты или в одной комнате. `signal`, `mute` и `pair-report` вне комнаты получают `bad-request`, как и `create` и `join` из комнаты. `leave` вне комнаты ничего не делает.
- Отправка не задерживает обработку других участников. У соединения своя очередь исходящих и задача-писатель, порядок сообщений одному адресату сохраняется. В очереди не больше 1024 сообщений и не больше 2 МБ: этого хватает на залп четырёх участников по 200 сообщений. Цикл чтения уступает event loop после каждого кадра, чтобы писатели успевали отправлять. При переполнении соединение закрывается кодом `4001`: клиент не читает. Это решение исполнителя (2).
- Соединение, закрытое сервером (`4000`, `4001`, `1008`), сразу отвязывается от места: место начинает ждать, `signal` к нему встаёт в очередь. Закрывающее рукопожатие ждёт не дольше 1 с, затем транспорт обрывается через расширение ASGI-scope `tete.transport.abort`, которое кладёт `TeteWebSocketProtocol`. Если расширения нет (uvicorn запущен без `--ws`), сервер один раз пишет WARNING без адреса и полагается на обычное закрытие.
- Каждое входящее сообщение, в том числе ошибочное, сначала проходит лимит частоты (см. «Лимиты»). Превышение закрывает соединение кодом `1008` без `error`, клиент вернётся по токену.

### Комната

**`create {name, net}`:**
1. Если создание комнат с этого IP превысило лимит — `rate-limited`.
2. Иначе сервер выдаёт новый id комнаты (при совпадении с существующей — новый) и новый id участника.
3. Ответ: `joined {resumed: false, peers: []}`.

**`join {roomId, name, net, resumeToken?}`.** Сначала проверяется токен: подпись верна и выдана для этого `roomId`. Дальше:

| Токен | Комната | Участник токена | Что делает сервер |
| --- | --- | --- | --- |
| действует | есть | в `peers` | Возврат. Если место ждёт 15 с и дольше, оно считается освобождённым, как в строке `left`, даже если уборка ещё не прошла. Если старое соединение ещё открыто, сервер закрывает его кодом `4000` без `peer-left` и без ожидания ответа: закрывающее рукопожатие ждёт не дольше 1 с, затем транспорт обрывается. Новое соединение привязывается к месту, `disconnected_at` сбрасывается, `net` обновляется, имя остаётся прежним. Ответ `joined {resumed: true}`, затем очередь `signal` по порядку, кроме сообщений отправителей, которых уже нет в `peers` (ждущие отправители остаются), очередь очищается. Остальным ничего не приходит |
| действует | есть | в `left` или вытеснен из него | Место освобождено: вход новичком (строка «нет или не действует»), новый id, `resumed: false` |
| действует | есть | нигде (комнату пересоздали после перезапуска) | Если комната полна — `room-full`. Иначе участник добавляется с прежним id, `joined {resumed: true}`, остальным `peer-joined` |
| действует | нет | — | Комната создаётся заново, участник с прежним id, `joined {resumed: true, peers: []}`. Лимит создания не применяется: подделать токен без секрета нельзя |
| нет или не действует | есть | — | Если в комнате 5 мест заняты (ждущие тоже занимают место) — `room-full`. Иначе новый id, `joined {resumed: false}`, остальным `peer-joined` |
| нет или не действует | нет | — | Лимит создания, затем комната создаётся, `joined {resumed: false, peers: []}` |

- `peers` в `joined` — все участники комнаты кроме себя, включая ждущих, с их `muted`.
- Новый `resumeToken` приходит в каждом `joined`. Он детерминирован: для той же пары комнаты и участника он тот же.
- `muted` после перезапуска сервера теряется: в `join` и `peer-joined` этого поля нет. Его восстанавливает правило клиента (решение исполнителя 12), протокол не меняется.
- `left` хранит не больше 1000 id, старые вытесняются первыми. При первом вытеснении комната ставит флаг `had_evictions`. С флагом действующий токен, чьего id нет ни в `peers`, ни в `left`, входит новичком, как из `left`. Без флага строка «нигде» работает как прежде. Генератор id избегает `peers ∪ left`, не больше 64 попыток, затем `room-full` (на практике недостижимо). Повтор вытесненного id (2⁻⁴⁰ на попытку) принят, как и для пересозданной комнаты.

**`signal {to, data}`.** `data` проверяется по исходному тексту: вложенность не больше 8 уровней, без `NaN`, `Infinity` и повторных ключей в одном объекте; иначе `bad-request`. Пересылается исходный текст `data` без пересборки, пересланный `signal` — до 65 538 байт (`to` → `from`). Если `to` — это сам отправитель или его нет в `peers` комнаты отправителя, сообщение молча отбрасывается: адресат мог только что уйти. Если адресат на связи, он получает `signal {from, data}`. Если адресат ждёт возврата, сообщение встаёт в его очередь. В очереди не больше 50 сообщений и 256 КБ, из них от одного отправителя — не больше 25: так один участник не вытеснит offer новичка. Сверх пределов новые отбрасываются, старые остаются: первым в очереди обычно лежит offer.

**`mute {muted}`.** Сохраняется у участника. Остальные участники на связи получают `mute {id, muted}`, ждущие узнают состояние из `peers` при возврате.

**`leave`.** Участник удаляется сразу, его id попадает в `left`, очередь выбрасывается. Остальные получают `peer-left`. Соединение остаётся открытым, с него можно снова войти.

**Обрыв соединения в комнате.** У участника `ws = None`, `disconnected_at = now`. Остальным ничего не приходит. Закрытие старого соединения при возврате (строка 1 таблицы) обрывом не считается: обработчик старого соединения проверяет, что место всё ещё привязано к нему, и только тогда отмечает обрыв.

**Уборка, раз в 1 с.** Участник, который ждёт 15 с и дольше, удаляется: его id попадает в `left`, остальным приходит `peer-left`. Комната, в которой не осталось участников, удаляется сразу — и при `leave`, и при уборке — вместе с `left`. Точность — 1 с: `peer-left` приходит через 15–16 с после обрыва.

### `resumeToken`

- Формат: `<peerId>.<подпись>`, где подпись = base64url без `=` от HMAC-SHA256(`RESUME_SECRET`, `"v1\n" + roomId + "\n" + peerId`). Длина 52 символа, укладывается в формат `ResumeToken` из модели.
- Проверка — `hmac.compare_digest`. Токен с неверной подписью, неверным форматом или выданный для другой комнаты считается недействующим, `bad-request` он не вызывает.
- `RESUME_SECRET` берётся из окружения. Если его нет или он короче 32 символов, приложение не запускается и сообщает об этом без значения секрета.

### Лимиты (1.7)

- **Ключ:** IPv4 — адрес целиком, IPv6 — префикс /64: домашнему абоненту выдают целую подсеть /64, и лимит по полному адресу обходился бы сменой адреса. IPv4, отображённый в IPv6 (`::ffff:a.b.c.d`), считается как IPv4.
- Адрес разбирается через `ipaddress`. Строка, которая не разбирается, и отсутствующий адрес идут в общий ключ `"unknown"`.
- **Места на ключ — не больше 20:** открытые соединения плюс ждущие места участников, вошедших с этого ключа. Ждущее место держит слот, пока его не удалили или не вернули: иначе места копились бы сверх 20 без соединений. Слот освобождается ровно один раз. Превышение — отказ рукопожатия до `accept` (HTTP 403).
- **Рукопожатия:** не больше 30 за 60 с на ключ, превышение — отказ до `accept`.
- **Входы** (`create` и `join` вместе): не больше 30 за 60 с на ключ, превышение — `rate-limited`.
- **Создание комнат:** не больше 10 за 60 с на ключ (решение человека 1), превышение — `rate-limited`. Отклонённые попытки в окно не входят.
- **Частота сообщений** на соединение, токен-бакеты: сообщения — запас 200, пополнение 20 в секунду; байты — запас 256 КБ, пополнение 32 КБ/с. Байты на ключ, общий бакет всех его соединений: запас 512 КБ, пополнение 64 КБ/с. Считаются и ошибочные сообщения. Превышение — закрытие кодом `1008`. Разбор угроз показал, что `signal` на 64 КБ из мелких элементов стоит около 25 мс процессора на разбор и пересборку, и без лимита одно соединение занимает единственный event loop. Оценка трафика входа в комнату на пятерых — около 100 сообщений и 50 КБ за 1–2 с, числа сверяются с живым трафиком на этапе 4.
- **Очереди исходящих на ключ:** сумма не больше 4 МБ. Сверх — кодом `4001` закрывается самая большая очередь этого ключа.
- **Глобально:** соединений не больше 1000, комнат не больше 500, байтов во всех очередях (исходящих и ждущих) не больше 128 МБ. Сверх предела — отказ рукопожатия, `rate-limited` на создание комнаты, отбрасывание в очередь ждущего. Если 128 МБ не хватает новому исходящему сообщению, кодом `4001` закрывается самая большая очередь сервера.
- Правило самой большой очереди для ключа и для сервера: чужое соединение закрывается, только если оно не текущий получатель и его закрытие освобождает недостающие байты. Иначе закрывается сам получатель: больше всех держит он сам, или бюджет заняли очереди ждущих.
- Скользящие окна чистятся при проверке и уборкой, пустые ключи удаляются.
- Пределы — константы в коде и строки таблицы «Константы» в CLAUDE.md. Тесты могут передать другие.
- IP нигде не логируется и не попадает в сообщения ошибок. Наш код держит ключ IP в памяти, пока у ключа есть места или непустые очереди и пока идут окна лимитов: не дольше 60 с после последнего соединения. Бакет байтов ключа пропадает через время пополнения, около 9 с.
- При `--proxy-headers --forwarded-allow-ips 127.0.0.1` IP приходит из `X-Forwarded-For` от Caddy, uvicorn берёт крайний правый адрес. Интеграционные тесты подставляют разные IP этим же заголовком. Если заголовка нет и адрес получился loopback, сервер один раз пишет WARNING без адреса: «X-Forwarded-For отсутствует, лимиты общие». Так ошибка в Caddyfile не превращает лимиты в общие для всего сервера незаметно. Проверки только loopback достаточно: сигналинг слушает `127.0.0.1`, поэтому любой прокси подключается с loopback. Если `--host` когда-нибудь поменяют, правило пересматривается.

### Сырой бюджет и keepalive

Лимиты выше видят только собранные текстовые сообщения. PING и фрагменты uvicorn обрабатывает сам, поэтому без отдельного слоя одно соединение занимало целое ядро, а PONG нечитающему клиенту копились в буфере записи (около 100 МБ за 6 с). Этот слой — `TeteWebSocketProtocol` в `app/wsproto.py` (решение человека 4).

- **Сырой бюджет соединения** считается в `data_received` до разбора, по всем кадрам: данные, продолжения, управляющие. Байты — запас 1 МБ, пополнение 64 КБ/с; кадры — запас 1024, пополнение 64/с. Сверх — обрыв транспорта без кадра закрытия, клиент видит `1006`.
- Числа стоят выше лимитов приложения: законный трафик на пределе упирается в `1008` приложения раньше. Кадры — фрагментация до 5 кадров на сообщение в залпе и 3 в потоке плюс управляющие кадры. Байты — 256 КБ приложения, одно чтение event loop (256 КБ), одно неполное сообщение (64 КБ) и заголовки 1024 кадров, около 590 КБ; скорость вдвое выше скорости приложения. Соотношения закреплены тестом.
- **Не больше 64 кадров в одном сообщении:** первый и продолжения; управляющие кадры внутри не считаются и сообщение не заканчивают. 65-й кадр — обрыв транспорта без кадра закрытия. Иначе клиент держал бы одно сообщение открытым около 17 минут капельной подачей ниже сырой скорости, а uvicorn хранил бы каждый фрагмент: 1,4–2,7 МБ на соединение. Замер в Edge 155 (Chromium): сообщения до 64 КБ уходят одним кадром, дробятся только сообщения больше примерно 131 000 байт. Клиент `websockets` отправляет итерируемое по кадру на элемент и пустой последний кадр. Поведение Chromium внутри Electron проверяется на этапе 4.
- **PONG** не отправляется, пока буфер записи соединения больше 64 КБ — верхней отметки транспорта по умолчанию. Эхо CLOSE из того же чтения остаётся.
- **Таймаут ping** (`--ws-ping-timeout 15`) обрывает транспорт. Раньше uvicorn звал `close()`, который при полном буфере ждал вечно, и место не начинало ждать. Теперь приложение получает обрыв, место ждёт 15 с, затем `peer-left`.
- Класс опирается на внутренности uvicorn, поэтому uvicorn закреплён ровно на `0.54.0`. Тест сверяет версию и переопределённые методы базового класса; обновление uvicorn проходит вместе с ним.
- Без флага `--ws` сервер работает, но без этой защиты и с WARNING из раздела «Соединение».

### Логи

- uvicorn пишет рукопожатия WebSocket с адресом клиента в `uvicorn.error` на уровне INFO, `--no-access-log` их не убирает. Фильтр на этом логгере отбрасывает записи о рукопожатиях `/ws` (принятых и отклонённых). Остальные сообщения uvicorn — запуск, остановка, ошибки — остаются.
- Фильтр ставится при импорте `app.main`, чтобы работать при запуске через `uvicorn app.main:app` с флагами из CLAUDE.md.
- Записи о рукопожатиях фильтруются по шаблону `'%s - "WebSocket %s"'` во всех вариантах: `[accepted]`, `403` и другие коды. Путь в них идёт вместе с query, это тоже проверяется.
- Фильтр отбрасывает записи ниже INFO от `uvicorn.*` и `websockets.*` независимо от `--log-level`: на DEBUG websockets пишет кадры, а `--log-level trace` — ASGI-сообщения с адресом и текстом.
- Свои логи сервера не содержат IP, SDP, кандидатов, `data`, id комнат, имён и токенов. Можно писать счётчики и коды ошибок. Ни одной записи на каждое сообщение. Раз в 60 с — сводная строка: соединения, комнаты, закрытия по лимитам.
- Исключения: обработчик `/ws`, задача-писатель и уборка перехватывают любое исключение и пишут только `type(exc).__name__`, без текста и `exc_info`. Для event loop ставится `set_exception_handler` с тем же правилом. Иначе `"Exception in ASGI application"` и `"Task exception was never retrieved"` выведут traceback, а `str(exc)` может содержать имя, id, токен или кусок `data`.
- У датаклассов состояния поля `name`, `ws`, `queue` и `net` — `repr=False`, у `name` в Pydantic-моделях — тоже.
- Ошибка настроек (`RESUME_SECRET` короткий) не печатает значение.

## Решения исполнителя

Не обсуждались с человеком, приняты как разумные значения по умолчанию:

1. `bad-request` не закрывает соединение. `room-full` и `rate-limited` — тоже.
2. Пределы из разбора угроз и финального ревью — все числа не из дизайна: очередь исходящих (1024 сообщения и 2 МБ, на ключ 4 МБ), сырой бюджет соединения, очередь ждущего по байтам (256 КБ) и по отправителю (25), рукопожатия и входы (30 за 60 с), частота сообщений (бакеты выше), глобальные пределы (1000 соединений, 500 комнат, 128 МБ очередей), ждущее место держит слот IP. Пределы частоты сверяются с живым трафиком на этапе 4.
3. При возврате имя участника не меняется, а `net` обновляется: после переподключения сеть могла смениться.
4. `join` с действующим токеном на несуществующую комнату не считается в лимит создания.
5. `signal` себе или неизвестному адресату отбрасывается молча.
6. Сверх 50 сообщений в очереди ждущего отбрасываются новые.
7. `leave` вне комнаты ничего не делает. `signal`, `mute` и `pair-report` вне комнаты — `bad-request`.
8. Формат токена — `<peerId>.<HMAC>` с меткой версии `v1` внутри подписи.
9. Без `RESUME_SECRET` (или если он короче 32 символов) сервер не запускается.
10. Известное следствие: если комнату удалили, потому что все ушли, участник, вернувшийся позже со старым токеном, создаёт её заново с `resumed: true`. Его старые P2P-соединения к этому времени уже закрыты, вреда нет.
11. Коды закрытия WebSocket со стороны сервера. Это не сообщения протокола, в схему они не входят, но перечисляются в «Протоколе сигналинга» CLAUDE.md:
    - `4000` — место занял новый вход с тем же токеном. Клиент не переподключается сам: иначе два экземпляра с одним токеном вытесняли бы друг друга до 10.3 (`requestSingleInstanceLock`);
    - `4001` — клиент не читает: переполнена очередь исходящих соединения, или его очередь самая большая при пределе ключа или сервера;
    - без кадра закрытия (клиент видит `1006`) — превышен сырой бюджет кадров или нет ответа на ping сервера;
    - `1008` — превышен лимит частоты сообщений;
    - `1012` — сервер останавливается или перезапускается; ставит uvicorn;
    - `1007` — текст не в UTF-8; ставит uvicorn;
    - `1009` — сообщение больше 64 КБ, в том числе после сборки фрагментов или разжатия; закрывает uvicorn.
12. `muted` после перезапуска сервера восстанавливает правило клиента: после каждого `joined`, если микрофон выключен, клиент отправляет `mute {muted: true}`. Оно добавляется в «Правила кода» клиента в CLAUDE.md рядом с решением 3 и реализуется в этапе 5.
13. Проверки «id из токена совпал с id другого участника» нет. Токен детерминирован, такого участника нельзя отличить от владельца места, а вероятность совпадения — 2⁻⁴⁰.

**Интеграционные — настоящий uvicorn в отдельном процессе:**

Тестовая фабрика читает `TETE_TEST_LIMITS` и `TETE_TEST_CLOSE_WAIT`; `start_server(ping_seconds=…)` сокращает интервал ping; `Client.settle()` — два круговых `ping` вместо фиксированных пауз; `stop_task()` отменяет и дожидается задач флуда.

Флуд PING и однобайтовых фрагментов обрывается, а другой клиент получает `pong` быстрее 1 с; трафик на пределах приложения закрывает приложение (`1008`), а не сырой слой; замёрзший клиент обрывается по таймауту ping, и другой участник получает `peer-left`.

  - вход и выход;
  - обрыв и возврат с очередью;
  - `resumed: false` после `leave`;
  - перезапуск сервера: процесс останавливается и запускается с тем же секретом, все возвращаются с прежними id;

## Разбор угроз

Спецификация прошла разбор STRIDE агентом `security-scanning:threat-modeling-expert` (2026-10-22). Принятые меры уже вписаны выше: лимит частоты сообщений, байтовые и глобальные пределы, ждущее место держит слот IP, ключ /64, частота рукопожатий и входов, логи и исключения, гонки возврата, предел очереди на отправителя.

**Меры для других этапов** — вписываются в текст пунктов CLAUDE.md:
- **2.3:** ключ лимита STUN тот же — /64 для IPv6.
- **3.1:** запись AAAA для домена сигналинга не публикуется (решение человека 5). Абоненту выдают /56 или /48, туннельный брокер бесплатно даёт /48 — это сотни и десятки тысяч ключей /64, одного абонента хватит на глобальные пределы. Голос по IPv6 от этого не зависит: кандидаты IPv6 собираются независимо от протокола сигналинга. AAAA появляется только вместе с ярусами лимитов /56 и /48.
- **3.2:** в `CMD` Dockerfile — флаг `--ws app.wsproto:TeteWebSocketProtocol`.
- **3.3, Caddy:**
  - `trusted_proxies` не задавать, тогда Caddy перезаписывает `X-Forwarded-For`;
  - проверить вживую лог ошибок `reverse_proxy`: пока uvicorn перезапускается, переподключение получает 502, и Caddy может записать его с `remote_ip`, `client_ip` и заголовками. Нужен фильтр или исключение `http.log.error`;
  - `stream_close_delay`, чтобы перезагрузка конфигурации не рвала WebSocket;
  - тайм-ауты чтения заголовков;
  - `.env` с правами 600, секрета нет в образе и в compose.
- **3.4:** ограничение одновременных соединений и SYN на `443/tcp` с одного источника через nftables — TLS стоит процессора до приложения.
- **3.5:** в логе нет предупреждения об отсутствии `X-Forwarded-For`.
- **4.2, 5.2, клиент:**
  - токен только в памяти, не в логах и отчётах о сбоях;
  - на `4000` клиент сам не переподключается;
  - переподключение с нарастающей задержкой;
  - правила 3 и 12.
- **4.6:** имена выводятся с `unicode-bidi: isolate`, против подмены через U+202E и символы нулевой ширины.
- **9.3:** `relayTrack.from` внутри `data` сервер не проверяет, клиент сверяет его с серверным `relay`.

**Принятые риски:**
- обладатель ссылки видит IP участников из SDP — так устроен P2P;
- посторонний со ссылкой может занять все места, выгнать его нельзя — `kick` нет;
- утёкший токен вместе с `roomId` позволяет занять место до смены `RESUME_SECRET`, смена — аварийный выключатель;
- логов нет, расследовать злоупотребление нечем;
- абоненты за CGNAT делят лимиты одного IP;
- распределённая атака со многих IP сверх глобальных пределов — вне возможностей одного VPS;
- uvicorn с `--proxy-headers` держит до 4096 последних IP клиентов в `lru_cache` проверки доверенных адресов — в памяти процесса, не на диске и не в логах (решение человека 6);
- предел очереди ждущего «25 от одного отправителя» обходится двумя местами в комнате: отброшенные сигналы восстанавливаются пересогласованием после возврата;
- токены не истекают, аварийный выключатель — смена `RESUME_SECRET`;
- обрывы сырым слоем и по таймауту ping не считаются в сводной строке логов.
